## 1. Design and pre-registration

**Comparison target: v1** (primary, same as every version for
comparability). The bar's clause 1 is head-to-head vs v1 (normal
rules, 100 games, alternating colours), clause 2 is ladder Elo vs
v1's 70.4 (identical 20 games/opponent, mcts_sims=100), clause 3 is
tactical pass rate vs v1's on the hard suite (12/29) and the old
suite (20/20). **Secondary head-to-heads, also pre-registered:**
v8 vs v0 (100 games) and a 100-game swap match vs v1 under the
tempo judge (the harness default). v3's Elo 107.5 is the current
best and is reported alongside for transparency.

**The improvement: v8 = v6's PUCT MCTS (v1 priors, 100 sims,
c_puct 1.5, win/block scans before search) with a LEARNED VALUE
FUNCTION as the leaf**, replacing v6's terminal-only leaf
(`ml/gomoku_ml/mcts_heuristic.py`, which this workstream does NOT
edit — it is owned by the parallel H1 workstream). New module
`ml/gomoku_ml/mcts_value.py` subclasses `HeuristicMCTS` and
overrides `_run_one` with a leaf hook; everything else (priors,
selection, backup, win/block scans, most-visited move choice) is
inherited unchanged, so any difference from v6 is attributable to
the leaf alone.

**Leaf design (decided BEFORE any eval).** Terminal check first,
net value otherwise:

- +1.0 if the player to move has any winning move (wins next move);
- -1.0 if the opponent has >= 2 winning moves (cannot block all);
- -0.25 if the opponent has exactly 1 winning move (must block —
  the search resolves which block; same value as v6's
  `_MUST_BLOCK_VALUE`);
- otherwise the trained net's value head output (tanh in [-1, 1],
  from the player-to-move perspective) on the 8-plane encoding of
  the leaf position.

The terminal cases are kept exact (a net cannot be trusted to
recognise a forced win/loss as reliably as a scan, and v6's defence
is already perfect — the leaf must not regress it); the net's job
is exactly the gap v6 exposed: valuing QUIET positions, where v6's
leaf is 0 and the search has no attack gradient.

**Net input at the leaf.** The full 8-plane encoding
(`gomoku_ml.encoding.encode`) is used. History planes are threaded
through the search path: `_run_one` carries the boards before each
move along the path (copied — the search mutates the board in
place), so planes 4–7 are the position 2/4 plies back along the
search path, exactly as in training (where they are the real game
history). The root's history is empty — the real game history
before the current position is unknown to `choose_move`, which
receives only the board — so leaves at depth < 2 have zeroed
history planes, the same as early-game training positions.
`last_move` is the move that led to the leaf (plane 2). CPU
inference, batch=1, torch threads 2.

**Data budget (FIXED before generation — this is the
pre-registered budget and it does not change with results).**
500 games at 100 sims/move, generated by the round-2 checkpoint
(resnet 32ch/4blocks, 192,714 params — copied from the main
worktree's `server/data/jobs/job-20261112-122716-9069f1/final.pt`
into this worktree at `ml/runs/b3-h2/round2-final.pt`; the copy
was verified: architecture resnet 32/4, 192,714 params, epoch 40,
step 6720) via the B2 batched path
(`ml/scripts/selfplay.py --concurrency 8 --max-batch-size 32`,
config seed 0, c_puct 1.5, Dirichlet α 0.3 / ε 0.25,
temperature 1.0 for 30 moves, max_moves 225, no resign
threshold — the round-2 job's own self-play settings). Expected
~1 hour at the measured batched rate (~570 games/hour on a quiet
VM, 444.7 in the coordinator's re-run; slower under H1
contention). The checkpoint file is gitignored data and is NOT
committed.

**Hold-out (decided BEFORE generation).** 10% of games — 50 games,
every 10th shard by index (game0009, game0019, ..., game0499) —
are held out as validation and NEVER used in training. The value
head's hold-out accuracy is the sign agreement between the net's
predicted value and the actual game outcome on non-draw positions
of held-out games, reported BEFORE any match, computed two ways:
(a) full planes as stored in the shards, and (b) history planes
(2, 4–7) zeroed, approximating leaf conditions where the root's
real history is unknown. Both numbers are recorded; (b) is the
one that predicts leaf quality.

**Value net (decided BEFORE training).** Smoke ResNet 16ch/2
blocks (per the batch-3 plan), trained from scratch with
`ml/scripts/train.py` (policy+value loss; only the value head is
used as the leaf): 20 epochs, batch 64, lr 0.002 cosine, warmup 20
steps, weight decay 1e-4, augmentation on, internal val_fraction
0.05 (for best.pt selection only — the game-level hold-out above
is the reported accuracy), torch threads 2, OMP_NUM_THREADS=2.

**Checkpoint selection (pre-registered rule).** After training,
compute the hold-out value sign-accuracy for BOTH `best.pt` (best
internal val loss) and `final.pt`; use the higher-accuracy one as
the leaf net, copied to `ml/runs/b3-h2/value-net.pt` (the path the
registry entry points at); record BOTH accuracies here. No other
selection criterion is used.

**Integration.** `ml/gomoku_ml/scoring.py` gains ONLY the
`ENGINE_VERSIONS[8]` registry entry
(`{"name": "scoring-v8", ..., "mcts": True, "mcts_sims": 100,
"value_checkpoint": "ml/runs/b3-h2/value-net.pt"}` — path relative
to the repo root, resolved in `ScoringPlayer.__init__`, overridable
via the `GOMOKU_V8_CHECKPOINT` env var) and a minimal dispatch hook
in `ScoringPlayer.__init__` (a version dict with a
`"value_checkpoint"` key instantiates `ValueMCTS` from
`mcts_value.py` instead of `HeuristicMCTS`). `baseline.py` is
frozen and untouched; `mcts_heuristic.py`, `mcts.py` and
`selfplay.py` are untouched. Per-leaf net eval cost and per-move
cost at 100 sims are measured and recorded before the matches.

**Eval seeds (pre-registered):** h2h vs v1: v8=100 / v1=200; h2h
vs v0: v8=100 / v0=200; ladder seed 100, 20 games/opponent,
mcts_sims=100; swap 100 games vs v1, balanced placement,

### 1.1 Direction change — fast heuristic loop (directed mid-batch by Yudong, ~23:00 PST 2026-11-13)

Yudong directed a method change on top of the batch-3 plan (see
`research/batch-3-direction-change.md`, committed on
`research/batch-3` after this branch forked — cited here, not
present in this worktree). The H1/H2/H3 direction and the 4-clause
"better" bar are UNCHANGED. What changed is the loss-analysis
method: statistics-first aggregates are replaced by a FAST
HEURISTIC LOOP — think like a human master (weak POINTS and weak
STRATEGIES, recurring structural mishandling), not aggregate
counts:

- After v8 is integrated, play 10 games against an opponent that
  produces losses to learn from (v0 or the MCTS ladder opponent —
  the matchup that exposes real weaknesses; v0 is the default
  choice: every search version in this program lost to it — v4
  0.37, v5 0.28, v6 0.41 — and it is fast, so 10 games take
  minutes; if an iteration produces no losses, switch opponents).
- Read EVERY move of every game. For each lost game, find THE
  losing move: the specific move where the game turned from
  drawable/winning to lost, verified with the solver or a deeper
  search — never guessed. (`ml/scripts/workup_loss.py` implements
  the corrected playout-oracle method: the actual move's playout
  must lose FIRST at the same seeds before an alternative counts.)
- Patch the algorithm so that, replayed to that critical position,
  it now plays the perfect move. Patches may be to the leaf
  combination, the search, or the training data (e.g. adding
  positions of the weakness class). Patches must fix the WEAKNESS
  (the structural cause), not the single position.
- Record each critical position + correct move as a regression
  test the patched engine must pass:
  `ml/gomoku_ml/regression_positions_v8.json` +
  `ml/tests/test_regression_v8.py`.
- Then play 10 more games and repeat. Bounds: max 4 fast-loop
  iterations (40 games) before validation, or stop when an
  iteration finds no new weakness class.
- Each fast-loop iteration is reported concretely in §4 below:
  game, losing move, perfect move + verification, patch, replay
  result. The fast-loop worked games ARE the loss analysis; the
  aggregate classification (via open four / missed blocks /
  missed preventions) becomes secondary.

### 1.2 Data path — B1 parallel self-play (10k dataset)

A separate B1 workstream is building multiprocessing parallel
self-play on top of B2 and will generate a 10,000-game dataset at
50 sims (expected location:
`/home/hatch/workspace/projects/gomoku-b3-b1/ml/runs/b3-b1-10k/` —
exact path confirmed in B1's report). The planned 500-game
B2-only run proceeds FIRST so v8 exists and can be validated; this
workstream does NOT wait idle for B1. If the 10k dataset lands
while this workstream is still running, the value net is retrained
on it and BOTH the 500-game and 10k-data versions' numbers are
reported (the 10k-data version counts for the bar if it is the
final form — the validation battery is re-run on it). If it does
not land in time, v8 is reported as-is and the 10k data carries
to the next version. The staged program (10k -> train -> full
eval; 50k -> eval; 100k+ -> eval, each stage gated on Elo
improvement, quality bar = the project's "good level" bar) is the
longer arc; v8 is its first step.

**Why this change — traced to the analysed gaps (iter-6 §2).**
v6 defends perfectly (166/166 losses via open four, 0 missed
blocks, 1 clean missed prevention in 1,061 threatened turns) and
still loses to v0 (0.41) and ties v1 (0.535, CI includes 0.50):
its terminal-only leaf values quiet positions at 0, so in quiet
positions the search has no gradient toward building an attack
and move choice falls back to priors plus noise (iter-6 §2.2(c):
the most-visited rule picked the high-prior move over the
high-value move). The direct A/B against the ladder MCTS
(9W-11L, then 21W-29L over 50 games) showed the leaf gradient
matters more than the prior quality. A learned value function is
the AlphaZero direction the project was built for, and it is the
one leaf design that can value attack-building in quiet positions
without a hand-built heuristic — the hand-built leaf has been
explored to its limit (v4/v5/v6). Batch 3 changes the evaluation,
not the search.
