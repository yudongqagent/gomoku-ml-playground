## 1. Design and pre-registration

**Comparison target: v1** (primary, same as every version for
comparability). The bar's clause 1 is head-to-head vs v1 (normal
rules, 100 games, alternating colours), clause 2 is ladder Elo vs
v1's 70.4 (identical 20 games/opponent, mcts_sims=100), clause 3 is
tactical pass rate vs v1's on the hard suite (12/29) and the old
suite (20/20). **Secondary head-to-heads, also pre-registered:**
v8 vs v0 (100 games) and a 100-game swap match vs v1 under the
tempo judge (the harness default). v3's Elo 107.5 is the current
best and is reported alongside for transparency.

**The improvement: v8 = v6's PUCT MCTS (v1 priors, 100 sims,
c_puct 1.5, win/block scans before search) with a LEARNED VALUE
FUNCTION as the leaf**, replacing v6's terminal-only leaf
(`ml/gomoku_ml/mcts_heuristic.py`, which this workstream does NOT
edit — it is owned by the parallel H1 workstream). New module
`ml/gomoku_ml/mcts_value.py` subclasses `HeuristicMCTS` and
overrides `_run_one` with a leaf hook; everything else (priors,
selection, backup, win/block scans, most-visited move choice) is
inherited unchanged, so any difference from v6 is attributable to
the leaf alone.

**Leaf design (decided BEFORE any eval).** Terminal check first,
net value otherwise:

- +1.0 if the player to move has any winning move (wins next move);
- -1.0 if the opponent has >= 2 winning moves (cannot block all);
- -0.25 if the opponent has exactly 1 winning move (must block —
  the search resolves which block; same value as v6's
  `_MUST_BLOCK_VALUE`);
- otherwise the trained net's value head output (tanh in [-1, 1],
  from the player-to-move perspective) on the 8-plane encoding of
  the leaf position.

The terminal cases are kept exact (a net cannot be trusted to
recognise a forced win/loss as reliably as a scan, and v6's defence
is already perfect — the leaf must not regress it); the net's job
is exactly the gap v6 exposed: valuing QUIET positions, where v6's
leaf is 0 and the search has no attack gradient.

**Net input at the leaf.** The full 8-plane encoding
(`gomoku_ml.encoding.encode`) is used. History planes are threaded
through the search path: `_run_one` carries the boards before each
move along the path (copied — the search mutates the board in
place), so planes 4–7 are the position 2/4 plies back along the
search path, exactly as in training (where they are the real game
history). The root's history is empty — the real game history
before the current position is unknown to `choose_move`, which
receives only the board — so leaves at depth < 2 have zeroed
history planes, the same as early-game training positions.
`last_move` is the move that led to the leaf (plane 2). CPU
inference, batch=1, torch threads 2.

**Data budget (FIXED before generation — this is the
pre-registered budget and it does not change with results).**
500 games at 100 sims/move, generated by the round-2 checkpoint
(resnet 32ch/4blocks, 192,714 params — copied from the main
worktree's `server/data/jobs/job-20261112-122716-9069f1/final.pt`
into this worktree at `ml/runs/b3-h2/round2-final.pt`; the copy
was verified: architecture resnet 32/4, 192,714 params, epoch 40,
step 6720) via the B2 batched path
(`ml/scripts/selfplay.py --concurrency 8 --max-batch-size 32`,
config seed 0, c_puct 1.5, Dirichlet α 0.3 / ε 0.25,
temperature 1.0 for 30 moves, max_moves 225, no resign
threshold — the round-2 job's own self-play settings). Expected
~1 hour at the measured batched rate (~570 games/hour on a quiet
VM, 444.7 in the coordinator's re-run; slower under H1
contention). The checkpoint file is gitignored data and is NOT
committed.

**Hold-out (decided BEFORE generation).** 10% of games — 50 games,
every 10th shard by index (game0009, game0019, ..., game0499) —
are held out as validation and NEVER used in training. The value
head's hold-out accuracy is the sign agreement between the net's
predicted value and the actual game outcome on non-draw positions
of held-out games, reported BEFORE any match, computed two ways:
(a) full planes as stored in the shards, and (b) history planes
(2, 4–7) zeroed, approximating leaf conditions where the root's
real history is unknown. Both numbers are recorded; (b) is the
one that predicts leaf quality.

**Value net (decided BEFORE training).** Smoke ResNet 16ch/2
blocks (per the batch-3 plan), trained from scratch with
`ml/scripts/train.py` (policy+value loss; only the value head is
used as the leaf): 20 epochs, batch 64, lr 0.002 cosine, warmup 20
steps, weight decay 1e-4, augmentation on, internal val_fraction
0.05 (for best.pt selection only — the game-level hold-out above
is the reported accuracy), torch threads 2, OMP_NUM_THREADS=2.

**Checkpoint selection (pre-registered rule).** After training,
compute the hold-out value sign-accuracy for BOTH `best.pt` (best
internal val loss) and `final.pt`; use the higher-accuracy one as
the leaf net, copied to `ml/runs/b3-h2/value-net.pt` (the path the

### 1.1 Direction change — fast heuristic loop (directed mid-batch by Yudong, ~23:00 PST 2026-11-13)

Yudong directed a method change on top of the batch-3 plan (see
`research/batch-3-direction-change.md`, committed on
`research/batch-3` after this branch forked — cited here, not
present in this worktree). The H1/H2/H3 direction and the 4-clause
"better" bar are UNCHANGED. What changed is the loss-analysis
method: statistics-first aggregates are replaced by a FAST
HEURISTIC LOOP — think like a human master (weak POINTS and weak
STRATEGIES, recurring structural mishandling), not aggregate
counts:

- After v8 is integrated, play 10 games against an opponent that
  produces losses to learn from (v0 or the MCTS ladder opponent —
  the matchup that exposes real weaknesses; v0 is the default
  choice: every search version in this program lost to it — v4
  0.37, v5 0.28, v6 0.41 — and it is fast, so 10 games take
  minutes; if an iteration produces no losses, switch opponents).
- Read EVERY move of every game. For each lost game, find THE
  losing move: the specific move where the game turned from
  drawable/winning to lost, verified with the solver or a deeper
  search — never guessed. (`ml/scripts/workup_loss.py` implements
  the corrected playout-oracle method: the actual move's playout
  must lose FIRST at the same seeds before an alternative counts.)
- Patch the algorithm so that, replayed to that critical position,
  it now plays the perfect move. Patches may be to the leaf
  combination, the search, or the training data (e.g. adding
  positions of the weakness class). Patches must fix the WEAKNESS
  (the structural cause), not the single position.
- Record each critical position + correct move as a regression
  test the patched engine must pass:
  `ml/gomoku_ml/regression_positions_v8.json` +
  `ml/tests/test_regression_v8.py`.
- Then play 10 more games and repeat. Bounds: max 4 fast-loop
  iterations (40 games) before validation, or stop when an
  iteration finds no new weakness class.
- Each fast-loop iteration is reported concretely in §4 below:
  game, losing move, perfect move + verification, patch, replay
  result. The fast-loop worked games ARE the loss analysis; the
  aggregate classification (via open four / missed blocks /
  missed preventions) becomes secondary.

**THE VALUE FUNCTION DID NOT GENERALIZE — the central finding of
this iteration.** On TRAINING data the net scores 0.9088 sign
agreement (MSE 0.2577, consistent with the train value loss);
on held-out games from the SAME generator it scores 0.44
(full planes) — below chance, and worse than a constant-0
predictor (MSE 1.74 vs 1.0). It is worst exactly where the
outcome should be most predictable:

| Position bucket (holdout, final.pt) | Sign agreement | MSE | mean\|v\| |
|---|---|---|---|
| Plies-from-end 0–2 (game nearly over) | 0.3600 | 2.009 | 0.780 |
| Plies-from-end 3–9 | 0.3657 | 2.089 | 0.764 |
| Plies-from-end 10–19 | 0.4520 | 1.824 | 0.733 |
| Plies-from-end 20+ (early/mid) | 0.4671 | 1.556 | 0.591 |
| TRAIN plies-from-end 0–2 (same net) | 0.9763 | 0.101 | 0.889 |
| TRAIN plies-from-end 3–9 | 0.9822 | 0.070 | 0.906 |
| TRAIN plies-from-end 20+ | 0.8445 | 0.417 | 0.651 |

The net memorized the 450 training games (each game's positions
are unique fingerprints it can identify and recall the outcome
of) and learned no generalizable value function; on unseen games
it is confidently wrong late (mean|v| 0.78 at 0.36 accuracy) and
at chance in mid-game. (Caveat: positions cluster by game, so
the effective sample size is ~50 games, not 2,109 positions —
0.44 vs 0.50 is within game-level noise; the robust claims are
"no signal" and "MSE far above the constant predictor", not the
exact degree of anti-correlation.) Plausible mechanism for the
late-game inversion: the net's dominant late feature is "the
opponent holds a four → losing", which is right 1 ply before the
end (the side to move loses) but wrong at the final position
(the side to move holds the winning move while the opponent's
four is still on the board); memorization masked this on train
(0.976) but it dominates on unseen games. Reference point: the
ROUND-2 net itself (the data generator, trained on ~400 of its
own games) scores 0.4955 / MSE 1.5483 on this holdout — also
chance-level — so weak-play game outcomes in this distribution
carry little position-predictable signal at this data scale.
The internal random-sample val split (value MSE ~0.45) is leaky
and optimistic: positions 1 ply apart in the same game are near-
duplicates, so it measures memorization, not generalization.
**Consequence for v8:** the leaf values are confident noise
(mean|v| 0.66, uncorrelated with outcomes). v8 is evaluated as
pre-registered anyway — the evals measure what a memorized-value
leaf does to the search — but the realistic expectation is v8 ≈
v6 or worse, and the fast loop (§4) will treat leaf noise as the
prime suspect weakness class. The structural fix is data scale
(B1's 10k set, §1.2) and/or a training setup that cannot
memorize game identities (far more games, stronger play, early
stopping gated on game-level hold-out) — not more epochs on 500
games.

  81 × ~2 ms ≈ 0.25 s/move. Real match timings (smoke + battery)
  are the numbers that matter; they are recorded with the
  matches in §5. Expectation: 100-game matches take 20 min
  (quiet VM) to several hours (contended VM) — run one at a
  time, in the background.

## 4. Fast heuristic loop (the loss analysis)

Per the direction change (§1.1), the fast-loop worked games ARE
the loss analysis; aggregate classification is secondary. Each
iteration: 10 games vs the weakness-exposing opponent, every move
read, THE losing move per lost game verified (solver / deeper
search / corrected playout oracle), patch to the structural cause,
regression position recorded, replay verified.

### 4.1 Iteration 1

**Match: the 20-game smoke vs v1 (seeds 100/200) — 5W-13L-2D**
(§5.2). The 13 lost games are the iteration's material (a
loss-producing opponent, as the direction change requires).
Aggregate first (`classify_losses.py`): 13/13 losses via open
four, 0 missed blocks, 0 clean missed preventions in 43
threatened turns — the same shape as v6's losses, so the
classifier alone cannot see the weakness. Every lost game was
then read move by move (viewer: `ml/scripts/show_game.py`;
threat trajectories and saving-move enumeration:
`ml/scripts/find_saving_move.py`).

**Worked games (2, 5, 6 — the three distinct lines; games 8, 9,
17 repeat 6, 5, 5):**

- **Game 2** (v8 Black, 32 plies). First hypothesis: ply 28,
  v8 played (4,9) instead of (4,5), letting White play (4,5)
  and complete TWO fours at once (row 4 + diagonal). Checked:
  at ply 28 White ALREADY had 1 winning move and 6 threat
  moves (moves creating ≥2 winning moves); the (4,5)
  "prevention" leaves White with 1 win + 2 threats — WORSE
  than (4,9) (0 wins, 1 threat, plus 2 own threats) by
  exhaustive enumeration, and the 400-sim deeper search (v8
  AND v6) also plays (4,9). Threat trajectory: T=0 until ply
  22, when White already holds 2 creators. At ply 20 v8's
  (5,7) is the best move by every 1-ply measure (own win + 3
  own threats) — but White's FORCED block (5,6) also builds
  White's threats. **No single losing move.**
- **Game 5** (v8 White, 23 plies). First hypothesis: ply 19,
  v8 played (4,11) instead of filling the gap (5,9) in Black's
  broken three. Checked: (5,9) leaves Black with 2 threats,
  (4,11) leaves 1 — (4,11) is (tied) best, and 400-sim search
  plays (8,7), also 1 threat. At ply 15 every candidate move
  leaves Black 0/0 — the 1-ply criterion cannot distinguish
  any move. **No single losing move.**
- **Game 6** (v8 Black, 26 plies). First hypothesis: ply 22,
  v8 played (10,9) instead of (8,10). Checked: (8,10) leaves
  White 1 win + 4 threats; (10,9) leaves 0 wins + 2 threats
  (best). 400-sim search also plays (10,9). **No single
  losing move.**

**The finding (and a correction of my first hypothesis): the
losses have NO single losing move.** v8's moves are locally
optimal at every checked ply (best or tied-best by exhaustive
threat enumeration, confirmed by 400-sim search). The games
are lost by slow accumulation: v1's 1-ply heuristic scorer
values threat-building consistently, while v8's search cannot
see the opponent CREATING an open four one ply ahead — the
leaf only scores positions where a winning move already
exists, and the tree never explores the opponent's quiet setup
moves deeply enough for the −1 to propagate. By the time the
opponent holds 2+ creators, no single move saves the game
(replay: at game 2 ply 28, game 5 ply 19, game 6 plies 20/22,
NO safe move exists — `threat_filter_used=0`, best effort).
This is the same "no single losing move" shape iter-6 §2.2
found for v6 — and it is exactly the gap v3's 2-ply threat
check closes (v3, Elo 107.5, is the strongest version).

**Patch (structural cause, not a position): v3's 2-ply threat
check, ported to the MCTS root.** `ValueMCTS.choose_move`
(`ml/gomoku_ml/mcts_value.py`, override — the parent file is
H1-owned and untouched): after the PUCT search, if the
opponent has creators (`scoring._opponent_creators`), the
choice is restricted to safe moves
(`scoring._move_is_safe`: forcing, or no creator remains
live); if no root child is safe, the most-visited move is
played (best effort, as in v3). With no creators the choice is
exactly the parent's. Cost: one creators enumeration per move
(~0.15 s). `threat_filter_used` counts restricted choices.

**Verification:**
- Tactical: old **20/20**, hard **29/29** (was 24/29 — all 5
  prevention fails fixed, no setup/VCF regression).
  `research/iterations/batch-v8-tactical-patched1.json`.
- Replay: game 2 ply 22 — patched v8 plays (8,9), safe
  (`threat_filter_used=1`); the later T≥2 positions have no
  safe move (already lost — the patch prevents reaching them,
  it cannot rescue them).
- Regression: `ml/gomoku_ml/regression_positions_v8.json` (5
  tactical prevention positions + smoke game 2 ply 22) +
  `ml/tests/test_regression_v8.py`; filter unit tests in
  `ml/tests/test_mcts_value.py`. Targeted suites: 65 passed.

### 4.2 Iteration 2

**Match: 10 games vs v0 (seeds 1001/2001), patched v8
(threat check): 0W-10L-0D** — in 60 s, games of 20–29 plies.
8 distinct lines; 10/10 losses via open four, 0 missed
blocks. Far worse than v6's 0.41 vs v0. First suspect was the
iteration-1 patch itself — **A/B refuted it**: the UNPATCHED
v8 (threat check reverted, same seeds) also loses 0-10
(`fast-v8-vs-v0-iter2-unpatched.json`). The patch is not the
cause. Second A/B: **v6 vs v0, same seeds: 4W-4L-2D (0.50)**,
reproducing batch 2. So the VALUE NET is the problem: v8's
search with the full net value loses 0-10 where v6's
terminal-only leaf (0 in quiet positions) scores 0.50.

**Worked game (iter2 game 0, v8 Black, 28 plies):** White
wins on the diagonal (4,6)–(8,10). At ply 24 (v8 to move)
White already holds 4 creators and NO safe move exists
(verified exhaustively) — the position was lost before ply
24, as in iteration 1. The divergences from v6's games start
at ply 1–4 (the OPENING): v8 replies (7,9) to (7,7) where v6
plays (5,5)/(5,7)/(5,9) — the net's opening values are noise
(it trained on temperature-sampled weak self-play, where
openings are random), and MCTS exploits the net's
overvaluations (the optimizer's curse): with the full net
value the search overrides the v1 priors with noise, and v0's
direct heuristic attacks convert the loose positions in
20–29 plies. The net's 0.72 holdout accuracy does not
transfer: the holdout measures outcome prediction in the
weak-self-play distribution, not against heuristic opponents.

**Patch (structural cause): shrink the net value toward the
terminal value (0 in quiet positions).** `_leaf_value` now
returns `VALUE_WEIGHT * net_value` for quiet positions
(`ml/gomoku_ml/mcts_value.py`); terminal cases are exact and
unaffected. Weight tuned on the v0 match (same seeds
1001/2001, 10 games each — cheap at ~1–2 min per match):

| VALUE_WEIGHT | vs v0 (10 games) |
|---|---|
| 1.0 (full net) | 0W-10L (0.00) |
| 0.5 | 2W-8L (0.20) |
| **0.25** | **6W-4L (0.60)** |
| 0.0 (= v6, no threat check) | 4W-4L-2D (0.50) |

The relationship is not monotone: the net HELPS at low weight
(attack gradient as a weak signal) and HURTS at high weight
(it overrides the priors). α=0.25 is kept — tuning stopped
here to avoid overfitting the 10-game v0 sample (finer steps
would be noise). The threat check from iteration 1 stays (it
fixed tactics 29/29; the A/B shows it is not the v0 problem).

**Verification:**
- Tactical (α=0.25): old **20/20**, hard **29/29** — the shrink
  does not regress tactics.
  `research/iterations/batch-v8-tactical-patched2.json`.
- Patched smoke vs v1 (20 games, seeds 100/200):
  **11W-7L-2D, win rate 0.60, 95% CI [0.3866, 0.7812]**
  (`batch-v8-vs-v1-smoke-patched.json`, 384 s) — vs unpatched
  5W-13L-2D (0.30). As Black 7W-2L-1D (0.75), as White
  4W-5L-1D (0.45): the normal Black edge is restored

  n=20 — the 100-game battery decides.
- Unit tests: leaf shrink bound + quiet-value test updated;
  targeted suites green (22 passed).
