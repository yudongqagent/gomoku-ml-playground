**Method (carried over from batch 3/4):** the fast 10-game loop —
play 10 games against an opponent that produces losses to learn
from (v0 is the default), read EVERY move of every game, find THE
losing move per game (verified with the solver or a deeper search
— never guessed), patch the algorithm so that, replayed to that
critical position, it plays the perfect move, and record each
critical position + correct move as a regression test. Then play
10 more games and repeat. Max 4 fast-loop iterations (40 games)
before validation, or stop when an iteration finds no new
weakness class. Patches must fix the STRUCTURAL cause, not the
single position. The full 4-clause validation battery (100-game
matches + ladder) runs on the FINAL patched v14 only. Fast-loop
games use development seeds (1001/2001, 1002/2002, ...) distinct
from the bar battery's pre-registered seeds (100/200), so no
development game overlaps an eval game.

## 1. Design and pre-registration

**Comparison target: v7** (the reference — ladder Elo 190.8, on
master; the bar's clause 1 is head-to-head vs v7, normal rules,
>= 100 games, alternating colours). Clause 2 is ladder Elo vs
v7's 190.8 (identical 20 games/opponent, mcts_sims=100).
Clause 3 is tactical pass rate vs v7's (20/20 old + 29/29 hard).
Clause 4 is all test suites green (ml pytest, npm test, tsc).
**Secondary head-to-heads, also pre-registered:** v14 vs v0
(100 games) and a 100-game swap match vs v7 under the tempo
judge (the harness default). Non-transitivity is recorded
prominently.

**The improvement: v14 = v7's PUCT MCTS with the gradient leaf's
input scores ported from the v0 kernel to the v1 5-window
scorer.** Everything else is v7 unchanged: 100 sims, c_puct 1.5,
v1 priors over all candidates, win/block scans before search,
most-visited root child, terminal leaf values identical. The
ONLY change is the quiet-leaf gradient: v7 counts threat breadth
from the portable kernel's attack-only scores, which port v0's
contiguous-run scoring and are BLIND to broken fours; v14 counts
the same breadth from a vectorized port of v1's 5-window attack
scorer (`scoring.score_attack`), so broken-four creations and
gap-three creations count as the strong threats they are.

**The defect being fixed, measured (Step 0, §1.1).** A move
creating a broken four (XX_XX) scores 20,006 in v1 but 130 in
v0 (developing tier at best); a gap-three creation scores 4,006
in v1 but 130 in v0. On 304 quiet positions from the v7-vs-v1
records, the v1 breadth difference differs from the v0 breadth
difference in 97.4% of positions, and the mean total strong-move
count is 8.51 (v1) vs 4.61 (v0) — the v1 gradient sees nearly
twice as many strong moves. This is a known, specific,
measurable defect in v7's leaf, not a new leaf design: the
gradient's FORM (breadth count, tanh squash, cap) is unchanged;
only its input scores are corrected.

**The v1 kernel (`ml/gomoku_ml/kernel_v1.py`).** A vectorized
NumPy port of `scoring.score_attack` for all 225 cells at once:
per direction, per-window friendly/opponent counts, empty-cell
position sums, and outside-cell emptiness are computed on the
grid of window starts from shifted padded masks; the window
score depends on the move's position within the window only
through the open-four check (`empty_idx = empty_sum - move_idx`),
so position-independent base scores are computed once per
direction and only the open-four upgrade is recomputed per
position; per-direction bests are max-accumulated with slice
views (no padding, no intermediate arrays). Max-per-direction
and the double-threat bonuses are ported exactly (the window
kind is a function of the best score: 10M -> five, 200k/20k ->
four, 4k -> open three, so the Python code's first-max-wins tie
order cannot change the kind). v1 quirks are ported, not fixed:
occupied cells score as `score_attack` scores them (the move
cell's own content counts toward the window counts), and a
window holding 5 friendly stones scores 0 (the Python
`own == 6` fall-through).

**Cross-check (0 mismatches required, as in the original kernel
work).** `ml/tests/kernel_v1_fixtures.json` holds the SAME 60
positions as the v0 fixtures (20 tactical, 3 structured, 37
random midgame) with frozen v1 attack reference scores for BOTH
players at all 225 cells, generated by
`ml/scripts/generate_kernel_v1_fixtures.py` from
`scoring.score_attack`. `ml/tests/test_kernel_v1.py` checks the
kernel against the frozen reference AND a live
`scoring.score_attack` reference, both players, all cells, all
fixtures, plus live cross-checks on six hand-built boards rich
in broken fours, gap threes, and edge patterns. Result: **0
mismatches on every layer** (60 fixtures x 2 players x 225
cells frozen + live, plus the 6 targeted boards). The kernel is
NumPy/CPU only: WebGPU/Metal re-sync happens ONLY if v14 passes
the bar (batch-5 plan).

**The scale question (pre-registered).** The v1 attack scores
have a different scale than the v0 kernel's, so the breadth
thresholds and the tanh squash are re-derived from the v1 score
distribution — the leaf's effective range is NOT silently
changed:

- Thresholds are derived from the v1 PATTERN CLASSES, not
  measured: strong = a move creating a four or an open three,
  i.e. v1 attack >= 4000 (no combination of sub-4000
  per-direction values reaches 4000: the strongest sub-open-three
  direction is a three at 400, 4 x 400 = 1600, and the
  double-threat bonuses require a four or an open three);
  developing = a move creating a half-open three (400) or an
  open two (80), i.e. 80 <= attack < 4000 (the strongest
  sub-open-two combination is 4 x two = 40 < 80). These are the
  v1 analogues of v7's v0 thresholds (strong >= 1000 =
  four/open-three maker; developing [100, 1000) = half-open-three
  / open-two maker). Breadth = strong + 0.25 * developing, as
  in v7.
- The tanh scale is re-derived from the MEASURED v1
  breadth-difference distribution by the SAME rule v7 used:
  scale ~= 1.8 x std (v7: scale 4 ~= 1.8 x std 2.26). Measured
  on the Step-0 sample (§1.1): std 4.09, so 1.8 x std = 7.36,
  rounded to **scale 7.5**. The scale is fixed here from the
  measured distribution, NOT tuned on any v14 eval result.
- **The cap stays ±0.2** — the cap (strictly below the smallest
  terminal value 0.25) is what made v7 pass, and it is kept
  unchanged: a static heuristic must never outweigh an exact
  terminal signal. The gradient's range is therefore identical
  to v7's; only its input scores and the (pre-registered)
  thresholds/scale change.

**What this change is meant to fix.** v7's gradient undervalues
broken-four setups relative to v1's scoring: a broken-four
creation is a four-maker in v1's terms (20k — a broken four is
a four, with the gap as its winning square) but a developing
move at best in v0's (~100-200), so v7's search systematically
under-rates lines that build broken fours — the very patterns
the open-four race turns on (every decisive game in every batch
is decided by an open four, and a broken four is a four that
costs the opponent a tempo to answer). If v14 still loses the race, the gradient's information
content is not the binding constraint (cf. v11's lesson that
the leaf is not the binding constraint in general) — but H3 is
explicitly tasked because this defect is specific and
measurable, and the battery decides.

### 1.1 Step 0 — cost and distribution measurement

`ml/scripts/bench_v14_leaf.py` on 346 boards replayed from
batch-v7-vs-v1.json (first 20 games, every 4th ply from ply 8;
304 quiet), median of 3 rounds x 50 calls, on this VM while the
parallel H1/H2 workstreams share it (absolute numbers are
contention-noisy; the ordering is what matters). The v7 numbers
re-measured here match iter-7's Step 0 (2.06 ms), so contention
was low during this run.

| Call | Median ms/call |
|---|---|
| `kernel_v1.attack_v1_both` | 5.64 (min 4.63, max 7.34) |
| v1 breadth gradient (full) | 5.76 (min 4.42, max 5.78) |
| `kernel_numpy.attack_both` (v7) | 2.12 (min 2.07, max 2.14) |
| v7 `_attack_gradient` (full) | 2.16 (min 2.16, max 3.47) |
| v6 `_terminal_leaf_value` | 1.61 (min 0.59, max 1.82) |

The v1 gradient costs ~5.8 ms per quiet leaf vs ~2.2 ms for
v7's — ~2.7x the leaf cost. At up to 100 leaf calls per move
that is at most ~+0.36 s/move over v7's ~0.95 s/move, so a
100-game match is ~75-90 min under contention. Affordable.
(First version of the kernel measured 21.5 ms/call; profiling
showed `np.pad` at 46% of the time (40 pads per call) plus the
per-position window-score recomputation. The slice-max rewrite
plus the base/open-four split cut it 3.8x to 5.6 ms, with the
cross-checks still at 0 mismatches.)

v1 breadth-difference distribution on the 304 quiet positions:
mean -1.42, std 4.09, p10 -8.00, p50 0.00, p90 3.25; |diff| >= 2
in 53.9%, >= 4 in 32.9%, >= 6 in 17.8%. (The negative mean:
the player to move typically holds less breadth than the side
that just moved — the positions come from real games where the
side to move is often responding. The tanh is symmetric, so
this shifts values without changing the scale derivation.)
Scale: 1.8 x 4.09 = 7.36 -> **7.5** (pre-registered above). At
scale 7.5 a real attack edge (diff +4) maps to 0.2*tanh(0.53)
= 0.098, a decisive edge (diff +8, top ~18%) to 0.157 — graded
signal, not saturated, and always below the terminal values.

v1 vs v0 breadth on the same 304 quiet positions: the breadth
difference differs in 296/304 (97.4%); the total strong-move
count differs in 266/304 (87.5%); mean total strong moves per
position 8.51 (v1) vs 4.61 (v0).

**Games 1 and 3 — the two blocks are indistinguishable to
every signal in the engine (NOT a v14 defect).** In both
positions Black holds exactly 2 creators, and the losing move
and the saving move ARE the two creator squares: both moves
kill all Black creators (0 after), both are non-forcing, and
their v1 scores are nearly tied (200169 vs 200107 in game 1;
204087 vs 200167 in game 3). The gradient prefers the losing
move in both cases — the v1 gradient AND the v0 gradient
(game 1: v1 +0.121 vs +0.046, v0 +0.061 vs +0.025; game 3: v1
+0.174 vs +0.146, v0 +0.119 vs +0.072, mover's perspective
after the move). And v7 makes the SAME mistake: replayed at
100 sims, v7's root picks the losing move in both positions
(game 1: 25 visits vs 18; game 3: 22 vs 14), with the same
q-ordering as v14. The difference between the two blocks is
purely positional — which square leaves White better placed
10 plies later — and no signal in the engine (v1 score,
creator counts, either gradient, q at 100 sims) separates
them. There is no leaf patch for this: the v1 kernel neither
caused it nor can fix it within the pre-registered design.

**Game 9 — the v1 gradient is RIGHT; the search starves the
saving move (exploration weakness, a KNOWN class).** A quiet
position (Black holds 0 creators). The saving move (4,6) is
v1 rank 6 (prior 0.044) and wins 3/3 by oracle; the played
(5,10) is v1 rank 1 (prior 0.074) and loses 3/3. The v1
gradient PREFERS the save (+0.064 vs +0.046) — the leaf points
the right way, where the v0 gradient points the wrong way
(+0.025 vs +0.049). But at 100 sims the save gets only 3
visits (vs 15 for the played move) and its q is noisy
(-0.060 vs +0.033, our-perspective q = -child.q), so
most-visited picks the loser. This is the same exploration
weakness class as v7's iter-1 game-3 xfail (saving move ranked
8th, prior 0.04, starved of visits) — a KNOWN open item, not a
new class, and not a leaf-value weakness: the leaf is doing
its job and the search budget is the constraint. No patch
within the pre-registered design addresses it (more sims is
not a leaf patch, and v10 showed more sims is not
monotonically better; raising the cap would violate iter-7's
lesson and the pre-registration).

**Game 0 — no losing move.** Walk-back over the last 8 turns:
from ply 18 on the actual move loses 3/3 but NO tested
alternative saves (top-6+forcing); at ply 16 and earlier the
actual move does not lose at all seeds. Distributed drift, not
a blunder (the iter-6 result).

**Loop stops here (stopping rule).** Iteration 1 found no new
patchable weakness class: games 1/3 fail identically for v7
and v14 (no leaf signal separates the moves); game 9 is the
known exploration-weakness class; game 0 has no losing move.
So the fast loop ends after 1 iteration (10 games) per the
direction change's stopping rule, with NO PATCH. The three
verified critical positions are recorded as regression xfails
(`ml/gomoku_ml/regression_positions_v14.json` +
`ml/tests/test_regression_v14.py`, 3 xfailed) — documented open
weaknesses for the next batch. The fast loop's positive
finding: in the one worked position where the gradients
disagree (game 9), the v1 gradient is right and the v0
gradient is wrong — the kernel fix points the leaf the right
way, even when the search cannot follow it at 100 sims.

## 5. What this means

**The v1-kernel gradient hypothesis is REFUTED as a
strength gain — with one real, durable win underneath it.**
The defect was real and measurable: the v0 kernel scores a
broken-four creation at ~130 where v1 scores it at 20,006,
and on real game positions the v1 breadth differs from the v0
breadth in 97.4% of quiet positions (mean strong moves 8.51
vs 4.61). The port is exact (0 mismatches on every
cross-check layer). And the leaf-level evidence is positive:
in the one fast-loop position where the gradients disagree
(game 9), the v1 gradient points at the saving move and the
v0 gradient points at the losing move; under swap rules v14
beats v7 more decisively (0.64, CI lower 0.5424) than under
normal rules (0.60, CI lower 0.5020), showing the edge is
not an opening artefact. But at match scale the gain is
marginal (clause 1 passes by 0.002) and it does not survive
the ladder: v14 loses the 20-game heuristic sample 9-11 and
lands at Elo -34.9 against v7's 190.8. The program's lesson
from v11 — the leaf is not the binding constraint — holds
again: fixing a real, specific, measurable defect in the
leaf's input scores buys a small head-to-head edge and
nothing on the ladder. The binding constraints are elsewhere:
White's inability to create an attack (0.48 vs v7 as White,
0.53 under swap), and the search's failure to explore
low-prior saving moves at 100 sims (game 9: the leaf was
right, the move got 3 visits).

**The non-transitivity is the sharpest result of this
iteration.** v14 beats v7 (0.60), v7 beats the heuristic
(15-5), yet v14 loses to the heuristic (9-11): v14 > v7 >
heuristic > v14. The ladder's heuristic opponent IS v0, and
v14's 100-game record against the same opponent is 60-40 —
so the 9-11 is within noise of the 100-game number (its CI
includes 0.60), and a 0.60 ladder score would still only give
roughly +70 Elo, below v7's 190.8. But the pattern is
consistent across samples: v14 scores LOWER against the
weaker v0 (0.60) than against v7 (0.60 — equal here, but v7
scored 0.665 vs v0 against 0.705 vs v1), and its Black game
against greedy play is worse than v7's (20 Black losses to
v0 vs v7's 13). The v1 gradient's denser threat signal seems
to help against a searching opponent (v14 ties the baseline
MCTS 10-10 where v7 lost 8-12) and hurt, or at least not
help, against greedy 1-ply play — the gradient rewards
building threats, and against an opponent that takes every
immediate threat at face value, the extra threat-building
does not convert. This is a hypothesis, not a verified
mechanism: the three worked Black losses to v0 (§2.6) show
distributed drift, no blunder, so there is no single
mechanism to point at.

**What survives.** The v1 kernel itself (`kernel_v1.py`, 0
mismatches, 5.6 ms/call) is a durable, exact, reusable
component: any future leaf, prior, or analysis that needs
v1 attack scores for all 225 cells at once now has a
verified vectorized path, 3.8x faster than its first version
after the slice-max rewrite. The fast loop's three
regression positions (all xfail) document the two open
weakness classes precisely: indistinguishable creator-blocks
(games 1/3) and the exploration starvation of low-prior
saving moves (game 9). And the swap result (0.64, CI
excluding 0.50) is the strongest swap number any version has
posted against its reference — worth remembering when the
next batch weighs the swap metric.

**What the next batch should try.** In priority order: (a)
White attack creation — the persistent weakness across all
versions, now the binding constraint on the head-to-head
(v14 wins as Black 0.72 and loses as White 0.48); (b)
exploration of low-prior forcing/saving moves — the leaf
already points the right way in game 9 and the search does
not follow it; (c) understanding the greedy-opponent gap —
why a denser attack gradient helps against search and not
against 1-ply play. NOT to retry: another leaf-input fix —
two leaf workstreams (v11's distribution fix, v14's kernel
fix) have now shown the leaf is not the binding constraint,
and the next gain has to come from the search or the
decision rule, not the leaf values. The v1 kernel stays
available for those; a WebGPU/Metal re-sync is still gated
on a version passing the bar.
